# WS API — запуск конвейера (`/run`)

Протокол связи UI (reline-web) с бэкендом-раннером (Python, `reline_ws/app.py`).

## Транспорт

- WebSocket. Один кадр = один объект, сериализованный в **MessagePack** (бинарные
  кадры WS; текстовые кадры не используются).
- **Одно соединение = один запуск.** После `done` соединение можно переиспользовать
  под новый `start`. Второй `start` поверх активного → `error`. Один запуск на
  весь сервер: `start`, пока занят воркер → `error {message: "worker busy"}`.

## Адрес

UI берёт адрес из query-параметра `api` адреса страницы:

```
https://cdn.example/reline/?api=ws://127.0.0.1:8000/run
```

Правила: `ws://`/`wss://` — как есть; `http://`/`https://` — автоматически
заменяются на `ws`/`wss`. Если параметра нет — из localStorage, затем дефолт
`ws://127.0.0.1:8000/run`.

## Конверт

Каждое сообщение — map из трёх полей:

| Поле | Тип    | Описание                                                 |
| ---- | ------ | -------------------------------------------------------- |
| `m`  | string | Имя метода                                               |
| `id` | uint32 | Id запроса (клиент инкрементит); в событиях — id запуска |
| `d`  | map    | Полезная нагрузка метода                                 |

## Методы клиент → сервер

### `start` — запуск конвейера

| Параметр   | Тип    | Обязателен | Описание                                                                                                 |
| ---------- | ------ | ---------- | -------------------------------------------------------------------------------------------------------- |
| `pipeline` | map    | да         | Конфиг **структурой MessagePack**: `{"nodes": [...], "preprocess": [...]}` (или плоский массив — легаси) |
| `root`     | string | нет        | Переопределение базы путей на один запуск (обычно не нужно: её задаёт запуск сервера)                    |
| `models`   | string | нет        | Переопределение папки моделей на один запуск                                                             |
| `configs`  | string | нет        | Папка конфигов: создаётся, если нет; оттуда работают `config_list/read/delete`                           |

```msgpack
{ "m": "start", "id": 1, "d": { "pipeline": { "nodes": [ { "type": "level", "options": { "low_input": 0, "high_input": 255, "low_output": 0, "high_output": 255, "gamma": 1.0 } } ],
                                            "preprocess": [] }, "configs": "configs" } }
```

`pipeline` — именно структура, а не JSON-строка: клиент пакует её как есть (msgpack
поддерживает вложенные map/array/str/числа нативно), сервер не парсит JSON. Строковая
форма больше не принимается.

Ответ: `accepted`, далее поток `progress` и в конце `done`.

#### Разрешение путей (`root` / `models`)

Базы путей — **параметры запуска сервера**, а не то, что обязан знать клиент:
UI знает только адрес раннера.

```bash
python app.py --root /data --models weights      # или
RELINE_ROOT=/data RELINE_MODELS_DIR=/data/weights uvicorn app:app
```

Обе необязательны, и без них поведение прежнее.

`root` — одна база на соединение. Путь из ноды, `configs` или `models`
разрешается так: если он **уже начинается** с `root` или является абсолютным —
оставляется как есть; иначе считается относительным и джойнится: `join(root,
path)`. Без `root` пути используются как заданы, поэтому старый конфиг с
абсолютными путями работает без правок, а портируемый может писать `"path":
"src"` и запускаться из любой папки.

`models` — отдельная база для файлов моделей (дефолт — `/content/models`): туда
`download` ставит модель и оттуда её берёт повторный запуск. Относительное
значение (`"weights"`) разрешается через `root` → `/data/weights`.

`start.d.root` и `start.d.models` остаются в протоколе как **переопределение на
один запуск** (полезно внешним клиентам); `ls.d.root` — свой на запрос. Если
`root` прислан, он запоминается соединением: последующий `ls` без своего `root`
листает от той же базы. Текущие базы видны в `/health` (`root`, `models`).

Фронтенд этого репозитория их не отправляет: в интерфейсе есть только строка
адреса.

#### Препроцессоры

При `start` конфиг делится на `preprocess` (скачивание моделей, распаковка) и
`nodes`. **Сначала выполняются препроцессоры**, затем конвейер. Препроцессоры
реальные: `download` кладёт модель в `RELINE_MODELS_DIR` (по умолчанию
`/content/models`) и переписывает `options.model` всех upscale-нод с этим именем
на установленный путь; `unarchive` распаковывает архив (или папку с архивами)
рекурсивно и удаляет исходники. Скачивание репортит байты (`bytes_done`/
`bytes_total`) и скорость.

### `stop` — прерывание работы

`d: {}`. Сервер отвечает `ok`; если работа шла, она завершается событием
`done` с `cancelled: true`.

### `echo` — хартбит

Клиент шлёт раз в **5 секунд**:

```msgpack
{ "m": "echo", "id": 2, "d": { "t": 1730000000000 } }
```

Сервер обязан **немедленно** вернуть такое же `echo` с тем же `d`. Смысл — не
дать прокси/NAT оборвать «молчащее» соединение и мерить живость: нет ответа
15 секунд — соединение считается мёртвым (клиент закрывает его сам). Инициатор
echo — только клиент; сервер не шлёт свои echo без запроса (иначе пинг-понг).

### `ls` — автодополнение путей (вход и выход)

```msgpack
{ "m": "ls", "id": 3, "d": { "path": "/fol" } }
```

Необязательные поля в `d`:

- `root: "/data"` — база для `path` в этом запросе (и для последующих `ls` без
  своего `root`): `{"path": "fol", "root": "/data"}` листает `/data/fol`. Без
  параметра используется база соединения (`root` из `start` или прошлого `ls`);
- `files_only: true` — вернуть только файлы (каталоги отбрасываются);
- `ext: ["pth", "pt"]` — только файлы с перечисленными расширениями (ведущие
  точки и регистр игнорируются); **каталоги не отсекаются** — клиент продолжает
  спуск по дереву (выбор пути к модели: папки + веса).

Ответ: `{ "m": "ls", "id": 3, "d": { "entries": ["folder", "folder2"], "dirs": ["folder", "folder2"] } }`,
где `entries` — отфильтрованные имена, `dirs` — подмножество `entries` из
каталогов (клиент дорисовывает «/» при дополнении).

Правило: часть пути после последнего «/» — префикс; возвращаются имена записей
каталога-родителя, начинающиеся с этого префикса:

- `/fol` → `folder`, `folder2` (дозаполнение хвоста);
- `/folder/` → все файлы и папки внутри `/folder` (слэш замкнулся — листинг папки);
- `/folder/dig` → `dig` (существующая запись — сама себя);

Путь разрешается через `root` так же, как пути нод.

### `config_list` / `config_read` / `config_delete`

Работают с папкой из параметра `configs` (создаётся при `start`, если нет):

```msgpack
{ "m": "config_list", "id": 4 }                              → { "entries": ["a.json", "b.json"] }
{ "m": "config_read", "id": 5, "d": { "name": "a.json" } }   → { "name": "a.json", "content": "…" }
{ "m": "config_delete", "id": 6, "d": { "name": "a.json" } } → ok
```

Без `configs` (или с именем, вырывающимся из папки) — `error`.

## Методы сервер → клиент

### `accepted`

`{ "m": "accepted", "id": 1 }` — запуск принят, работа началась.

### `progress`

Данные для прогресс-бара. Кадр подробный: этап, что именно делается, счётчики,
скорость и остаток.

```msgpack
{ "m": "progress", "id": 1, "d": {
    "percent": 42,          # u8 0..100, монотонно не убывает внутри фазы
    "phase": "process",     # preprocess | process — фаза, которой принадлежит шкала
    "stage": "process",     # download | unarchive | read | process | write
    "label": "Gaussian Blur", # человекочитаемое имя шага (нода, файл, модель)
    "node": "sharp",        # тип ноды по wire-словарю, если шаг привязан к ноде
    "done": 42,             # обработано единиц на этом этапе (изображения / байты / файлы)
    "total": 120,           # всего единиц на этом этапе, 0 если неизвестно
    "elapsed": 12.5,        # секунд с начала запуска
    "rate": 8.4,            # единиц в секунду на текущем этапе
    "eta": 9.3,             # секунд до конца запуска (оценка), null если неизвестно
    "bytes_done": 0,        # только download: скачано байт
    "bytes_total": 0        # только download: размер файла, 0 если сервер его не сообщил
  } }
```

| Поле           | Тип    | Обяз. | Описание                                                                       |
| -------------- | ------ | ----- | ------------------------------------------------------------------------------ |
| `percent`      | uint   | да    | 0..100, монотонно не убывает внутри фазы; на смене фазы сбрасывается в 0       |
| `phase`        | string | да    | `preprocess` (препроцессоры) или `process` (конвейер изображений)              |
| `stage`        | string | да    | `download`, `unarchive`, `read`, `process`, `write`                            |
| `label`        | string | нет   | что делается прямо сейчас: имя модели/архива/файла или подпись ноды            |
| `node`         | string | нет   | wire-тип ноды (`upscale`, `sharp`, …) — UI подставляет своё название           |
| `done`/`total` | uint   | нет   | счётчики текущего этапа; `total: 0` = размер неизвестен (например, архив)      |
| `elapsed`      | float  | нет   | секунд с `start`                                                               |
| `rate`         | float  | нет   | единиц/с текущего этапа                                                        |
| `eta`          | float  | нет   | оценка остатка в секундах; в кадре может отсутствовать                         |
| `bytes_*`      | uint   | нет   | только этап `download`: прогресс скачивания, когда сервер дал `Content-Length` |

Правила:

- `percent` может стоять на месте (шаг длинный), но не убывает; последний кадр
  запуска — `percent: 100`;
- запуск состоит из одной или двух фаз: `preprocess` (скачивание/распаковка) и
  `process` (конвейер). Каждая владеет шкалой 0..100 от начала: препроцессоры
  заполняют бар, затем приходит кадр смены фазы с `percent: 0`, и обработка
  начинает свою шкалу. Так длинное скачивание модели не отнимает у изображений
  почти всю полосу, а бар может начаться заново;
- в начале каждого этапа приходит кадр с `done: 0` и подписью этапа — UI успевает
  показать новый этап до того, как пойдут числа;
- сервер шлёт кадр не чаще ~4 раз в секунду (и не чаще, чем меняется `percent`),
  поэтому поток не забивает канал на тысячах изображений;
- поля `rate`/`eta` появляются после первого замера (обычно через ~0.5 с этапа).

Раскладка шкалы внутри фазы: препроцессоры в фазе `preprocess` делят 0..100 по
весу (`download` весит 4× против `unarchive`); в фазе `process` первые 5% шкалы
занимает чтение (листинг файлов), дальше изображения. Конфиг без препроцессоров
даёт одну фазу `process` и один бар. Конкретные доли — деталь сервера, UI
пользуется только `percent` и `phase`.

### `done`

Терминальное событие запуска. После него соединение свободно.

```msgpack
{ "m": "done", "id": 1, "d": { "ok": true, "cancelled": false, "output": "<строка-лог/результат>", "error": null } }
```

- Успех: `ok: true`, `output` — лог/результат (опционально).
- Отмена через `stop`: `ok: false, cancelled: true`.
- Ошибка выполнения: `ok: false, error` — сообщение. Соединение не закрывается.

Инвариант: **после `error` (или любой ошибки этапа) `done` не может быть
успешным**. Кадр `error` перед этим не отменяет ошибку — UI обязан показать оба,
поэтому клиент ведёт журнал запуска, а не одну строку статуса.

### `error`

Ошибка протокола/запроса (битый `pipeline`, `start` поверх активного и т.п.):

```msgpack
{ "m": "error", "id": 1, "d": { "message": "invalid pipeline", "fatal": false } }
```

`fatal: true` — сервер закроет соединение после отправки.

- [x] `configs`: папка создаётся при `start`; `config_list/read/delete`

## Сценарий

```
клиент                          сервер
  │ ── ws connect ───────────────▶ │
  │ ── start {pipeline: map} ─────▶ │
  │ ◀─────────────── accepted ──── │
  │ ◀─ progress {phase: preprocess, stage: download, label: "4x_a", bytes_done, rate} ──│
  │ ◀─ progress {phase: preprocess, stage: unarchive, label: "raws.zip", percent: 100} ──│
  │ ◀───── progress {phase: process, percent: 0} ─────│   ← сброс шкалы
  │ ── echo {t} ─────────────────▶ │  (раз в 5 с)
  │ ◀──────────────── echo {t} ────│
  │ ◀─ progress {phase: process, stage: read, label: "Folder Reader", done/total} ──│
  │ ◀─ progress {phase: process, stage: process, node: "sharp", done: 42/120, rate: 8.4, eta: 9} ──│
  │ ◀───── progress {percent: 100, stage: write} + done ────│
  │ ── stop ─────────────────────▶ │  (если жмут «Стоп»)
  │ ◀───── ok, done {cancelled} ───│
  │ ── ls {path:"/fol"} ─────────▶ │
  │ ◀───── ls {entries:[...]} ─────│
```

## Обрыв связи

Соединение теряет прокси, туннель, спящая вкладка или упавшая сеть — для
раннера это не ошибка конвейера:

- первая неудачная запись помечает соединение мёртвым, взводит отмену и делает
  все дальнейшие кадры no-op; в логе одна строка
  `client disconnected: cancelling the run`, без трейсбека `pipeline error`;
- запуск останавливается на ближайшем чекпоинте, busy-гейт освобождается, так
  что переподключившийся клиент получает `accepted`, а не `worker busy`;
- `done` в мёртвый сокет не отправляется.

Возобновления с середины нет: клиент, который хочет продолжить, переподключается
и повторяет `start` с тем же конфигом. Повтор дешёвый — установленная модель не
скачивается второй раз, листинг папки это один `scandir`, а запись просто
перезаписывает результаты. Клиент делает до 4 попыток с ростом паузы
(1/2/4/8 с) и затем сдаётся с одной строкой в журнале.

## Диагностика подключения

Кроме `/run` сервер отдаёт обычный HTTP `GET /health` →

```json
{
  "ok": true,
  "version": "0.2.0",
  "busy": false,
  "root": "/data",
  "models": "/data/weights"
}
```

Это разделяет две разные поломки, которые в браузере выглядят одинаково
(«websocket error», 502 в Network):

- **5xx или отказ на всех путях, включая `/health`** — процесс не запущен,
  упал или прокси стучится не в тот порт/хост. Смотреть лог uvicorn и
  `ss -ltnp` на сервере; код и протокол тут ни при чём;
- **`/health` отвечает 200, а `/run` не поднимается** — процесс жив, проблема в
  прокси: он не пропускает `Upgrade: websocket` (nginx нужны
  `proxy_http_version 1.1`, `proxy_set_header Upgrade $http_upgrade`,
  `Connection "upgrade"`, `proxy_buffering off`; Apache 2.4.47+ —
  `ProxyPass /run ws://… upgrade=websocket`) или обрывает соединение по
  таймауту.

Обычный `GET /run` возвращает `404`: маршрут принимает только WebSocket-upgrade.

Ответы снаружи читаются так (проверять `curl -o /dev/null -w '%{http_code}'
https://<host>/health`):

- `404` с коротким `text/plain` телом — отвечает сам туннель/гейтвей: хост
  больше не зарегистрирован (туннель перезапущен, сессия кончилась), сервер тут
  ни при чём. 404 **от FastAPI** выглядит иначе — это JSON `{"detail":"Not Found"}`;
- `502`/`504` — туннель жив, источник за ним нет: другой порт, `127.0.0.1`
  вместо `0.0.0.0`, мёртвый процесс;
- `/health` отвечает `200`, а `/run` не поднимается — дело только в апгрейде
  на прокси (см. конфиги выше).

Клиент шлёт `echo` раз в 5 с и считает соединение мёртвым после 15 с молчания,
поэтому idle-таймаут прокси сбрасывается трафиком; длинный прогон требует
`proxy_read_timeout` больше минуты (по умолчанию у nginx 60 с).
